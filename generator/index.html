Minimum integration

One model and one JSON file

An .mvpack is an ordinary, unencrypted ZIP. A generator with no thumbnail, settings or rich metadata can still produce a useful package.

Package contents
Generated-Model.mvpack
├── Generated-Model.stl
└── meshvault.model.json
meshvault.model.json
{
  "schema": "meshvault.model",
  "version": 1,
  "title": "Generated Model"
}
Do not replace the normal export. Add a separate “Export for MeshVault” action and reuse the exact model bytes produced by the existing exporter.

Optional reference files

Instructions and colour guides can travel with the model

Add instructions, PDFs, JSON generation parameters or other files to the ZIP and list their portable paths in documentFiles. MeshVault attaches them to the imported model and shows them through Documents or Related files.

Package contents
Generated-Model.mvpack
├── Generated-Model.3mf
├── meshvault.model.json
└── documents/
    └── instructions.pdf
Document references
{
  "schema": "meshvault.model",
  "version": 1,
  "title": "Generated Model",
  "documentFiles": [
    "documents/instructions.pdf"
  ]
}

Each model can include up to ten attachments of any file type, up to 10 MiB each. PDF files must have a PDF signature. Generation parameters remain attached files; MeshVault does not regenerate a model from them.

No Base64 required

Images can remain ordinary files

Put image bytes into the ZIP and reference their paths. This works with browser Blobs, Canvas PNGs, uploaded files and server-rendered images.

Package contents
Generated-Model.mvpack
├── Generated-Model.3mf
├── meshvault.model.json
└── images/
    ├── thumbnail.png
    ├── front.jpg
    └── detail.webp
Image references
{
  "schema": "meshvault.model",
  "version": 1,
  "title": "Generated Model",
  "thumbnailFile": "images/thumbnail.png",
  "extraImageFiles": [
    "images/front.jpg",
    "images/detail.webp"
  ]
}

PNG, JPEG, BMP, GIF and WebP are accepted, up to 50 MiB per image. Prefer file references for new integrations. Existing Base64 remains supported through thumbnailDataBase64 and extraImageDataBase64.

View every metadata field

Separate model and generator credit

Keep the generator associated with the design

author is the model designer. generatorName names the generating site or tool. An optional exportDonationUrl supplies its HTTPS support page, without credentials.

Generator attribution
{
  "schema": "meshvault.model",
  "version": 1,
  "title": "Generated Vase",
  "author": "Model designer",
  "generatorName": "Example Generator",
  "exportDonationUrl": "https://example.org/support"
}

Details show “Created by [author]”, “Generated with [generator]” and a discreet “Support [generator]” link. It opens only when clicked. Omit unknown authors and optional support links. The old donationUrl spelling is unsupported.

Never export printedStatus. It is personal library state. Printing advice and printSettingsJson remain supported.

Complete model exports

Include the files the model references

Package OBJ material files and texture maps, and glTF/GLB external buffers and images with their relative layout. Embedded data needs no extra file. Missing resources, remote or absolute references, and conflicting contents fail visibly.

ZIP paths cannot contain traversal segments. References inside model files may use relative parent segments only while they stay inside the package and library. Exact filename casing matters. Existing resources with different bytes are never overwritten.

Optional multi-model form

Several model files need a manifest

When one export intentionally produces several independent library items, use meshvault.models.json with one metadata object per model. Each object identifies its fileName and exact portable relativePath.

Multi-model outline
{
  "schema": "meshvault.models",
  "version": 1,
  "models": [
    {
      "schema": "meshvault.model",
      "version": 1,
      "title": "Base",
      "fileName": "base.stl",
      "relativePath": "Parts/base.stl"
    },
    {
      "schema": "meshvault.model",
      "version": 1,
      "title": "Lid",
      "fileName": "lid.stl",
      "relativePath": "Parts/lid.stl"
    }
  ]
}

Framework independent

Implement at the existing export boundary

  1. 1
    Find the current model export

    Identify the function that produces the final Blob, byte array, stream, buffer or file.

  2. 2
    Collect available information

    Use real values already held by the generator. Omit everything else.

  3. 3
    Create the standard ZIP

    Add model bytes, dependencies, JSON metadata, images and attached files.

  4. 4
    Return or download .mvpack

    Use MIME type application/vnd.meshvault.package+zip.

Use the project’s existing ZIP library. Browser JavaScript or TypeScript projects without one should use fflate or JSZip, including a pinned local copy for no-build sites. Do not hand-write ZIP records. No MeshVault-specific package is required.

Acceptance checks

Know when the integration is complete

  • Existing exports still work and produce the same model bytes.
  • An ordinary ZIP reader opens the .mvpack.
  • The model and correct metadata filename are present.
  • Metadata parses as UTF-8 JSON with schema version 1.
  • Every referenced image exists and contains a supported image.
  • All ZIP entry paths use / and contain no traversal.
  • Model dependencies and attachments are present and valid.
  • Generator credit and optional support links are separate from the model author.
  • Printed status is excluded.
  • Missing optional data does not block export.
  • Failures are shown instead of downloading a partial package.
